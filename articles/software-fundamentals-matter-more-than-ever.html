The Thesis — Code Is Not Cheap

Matt Pocock opens with a message of comfort for developers feeling their skills are becoming obsolete: software fundamentals matter now more than they ever have. His talk is a systematic argument, grounded in classic software engineering books, that the AI coding revolution doesn't make good engineering practices optional — it makes them essential.

After 18 months teaching developers to build with AI agents through his "Claude Code for Real Engineers" course, Matt has watched the same patterns emerge repeatedly. The developers who succeed aren't the ones who delegate everything to AI or who refuse to use it at all. They're the ones who fall back on engineering fundamentals — decades-old ideas that didn't break when AI arrived. They got more important.

The Specs-to-Code Movement — And Why It Fails

Matt begins by addressing the specs-to-code movement head-on. The premise is seductive: write a specification of how an application should work, use AI to turn it into code, and if there's a problem, go back to the spec — not the code. Change the spec, run the "compiler" again, get new code.

Matt tried it. The audience tried it. The result was universal:

"I would run it, and I would try not to look at the code, but I would look at the code. I got code out first, then I ran it again and got worse code. I did it again, I got even worse code. I kept running the compiler and I would just end up with garbage."

His diagnosis: specs-to-code is just vibe coding by another name. The idea that we can ignore the code and let it manage itself fundamentally misunderstands what makes software systems degrade.

Software Entropy — The Physics of Bad Code

Instead of trying to fix the "compiler," Matt went back to the classics to understand why iterative AI code generation produces progressively worse results.

A Philosophy of Software Design (John Ousterhout)

Ousterhout defines complexity as "anything related to the structure of a software system that makes it hard to understand and modify the system." A bad codebase is one that's hard to change. If you can't make changes without causing bugs, you have a bad codebase. Good codebases are easy to change.

The Pragmatic Programmer (Hunt & Thomas)

The concept of software entropy describes exactly what Matt was seeing. Entropy is the tendency of systems toward disorder and collapse. Every time you make a change to a codebase thinking only about that change — without considering the design of the whole system — the codebase gets worse. Each specs-to-code iteration was increasing entropy.

The Core Insight

There's an assumption driving the specs-to-code movement: "code is cheap." Matt disagrees emphatically:

"Code is not cheap. In fact, bad code is the most expensive it's ever been."

Why? Because if you have a codebase that's hard to change, you can't take advantage of what AI offers. AI performs exceptionally well in good codebases. It struggles in bad ones. Therefore: good codebases matter more than ever, which means software fundamentals matter more than ever.

Six Failure Modes and How Classic Engineering Fixes Them

Matt structures his practical advice around common AI coding failure modes, each paired with a proven software engineering principle and a concrete Claude Code skill.

Failure Mode 1: "The AI Didn't Do What I Wanted"

You had a clear idea in your head, but the AI built something completely different. The communication barrier between you and the AI is real.

The Book: Frederick P. Brooks' The Design of Design introduces the concept of the design concept — the invisible, ephemeral shared understanding of what you're building that floats between collaborators. It's not an asset you can put in a markdown file. It's the theory of the thing.

The problem: you and the AI don't share a design concept.

The Solution — "Grill Me" Skill:

"Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one by one."

This skill (from Matt's viral 13,000+ star GitHub repo) turns the AI into an adversary that asks 40, 60, even 100 questions before it's satisfied a shared understanding exists. The resulting conversation can be turned into a PRD or directly into issues for an AFK agent.

Matt's strong opinion: "This is better than the default plan mode in Claude Code. Plan mode is extremely eager to create an asset — it really wants to create a plan and start working. Whereas I think it's a lot nicer to reach a shared design concept first."

Failure Mode 2: "The AI Is Way Too Verbose"

You're talking at cross-purposes. The AI uses too many words, and it feels like you're not speaking the same language.

The Book: Eric Evans' Domain-Driven Design and the concept of ubiquitous language — a shared vocabulary where conversations among developers, expressions in code, and conversations with domain experts all derive from the same domain model.

The Solution — Ubiquitous Language Skill: A skill that scans the codebase, identifies terminology, and generates a markdown file with tables of all domain terms and their definitions. This file serves as a shared dictionary between you and the AI.

The impact goes beyond communication. By reading the AI's thinking traces, Matt discovered that the ubiquitous language file:

  • Improves planning quality — the AI reasons more precisely
  • Reduces verbosity — the AI thinks in less verbose terms
  • Improves implementation alignment — the code matches the plan more closely

"This has absolutely been a powerhouse. It's been unbelievably good."

Failure Mode 3: "It Built the Right Thing, But It Doesn't Work"

The AI understood what you wanted and built it, but the result is broken.

The obvious fix: feedback loops — static types (TypeScript), browser access for front-end apps, and automated tests. But even with these tools, the LLM doesn't use them well. It does too much at once, producing huge amounts of code before thinking to type-check or test.

The Book: The Pragmatic Programmer calls this "outrunning your headlights" — driving too fast for conditions. "The rate of feedback is your speed limit." Testing as you go and taking small deliberate steps is how you stay within the speed limit.

The Solution — Test-Driven Development (TDD): TDD forces the LLM to take small steps. Create a test first, make it pass, refactor. The red-green-refactor cycle prevents the AI from generating mountains of untested code.

Failure Mode 4: "Testing Is Too Hard"

TDD sounds great in theory, but testing is genuinely hard. There are interconnected decisions at every level:

  • How big a unit do you test?
  • What do you mock?
  • What behaviors do you test?

All of these decisions are dependent on each other. And here's the key insight: good codebases are easy codebases to test. The quality of your feedback loops depends on the quality of your code architecture.

The Book: Ousterhout's deep modules concept. Not shallow modules (many small modules with complex interfaces), but relatively few, large, deep modules with simple interfaces.

  • Deep modules: lots of functionality hidden behind a simple interface. You can look inside if you want, but you don't need to.
  • Shallow modules: not much functionality, complex interface. A codebase full of tiny blobs that the AI has to walk through and navigate — and often fails to understand.

AI is really good at creating shallow module codebases (lots of small files, lots of abstractions). But AI is bad at navigating them. It can't find the right module in time, doesn't understand all the dependencies, and loses track of the architecture.

A codebase full of deep modules is structured inside clear boundaries with interfaces on top. These interfaces are easy to test — you test at the boundary, verify through the interface, and you're done. This is a codebase that rewards TDD.

The Solution — "Improve Codebase Architecture" Skill: A reusable set of steps: explore the codebase, find related code scattered across shallow modules, and wrap it in deep modules with clean interfaces.

Failure Mode 5: "My Brain Can't Keep Up"

Everything is working — feedback loops are firing, code is shipping faster than ever. But you're exhausted. "Raise your hand if you've felt more tired than you have ever before in your development career."

A shallow-module codebase makes it harder for both the AI and your brain. You both need to keep all that scattered information in your head. A deep-module architecture simplifies this by letting you treat modules as gray boxes.

The Solution — Design the Interface, Delegate the Implementation:

For non-critical modules (not finance, not security-sensitive), you can:

  1. Design the interface carefully yourself
  2. Let AI handle the implementation inside
  3. Test from the outside through the boundary
  4. Don't review the internal implementation deeply

"I have found this has really saved my brain because I can just go — 'Okay AI, I'll let you handle what's inside the big blob. I'm just going to test from the outside and verify it.'"

Failure Mode 6: "The Architecture Keeps Degrading"

Whenever touching code, planning, or prompting, you need to be aware of the modules in your application. The module map needs to be part of your ubiquitous language. It needs to be built into your planning skills. Matt's PRD skill explicitly includes module changes and interface modifications.

The Book: Kent Beck — "Invest in the design of the system every day."

This is the fundamental difference between specs-to-code and what actually works:

  • Specs-to-code = divesting from system design. Ignoring the code. Letting entropy win.
  • Fundamentals-driven AI development = investing in system design daily. Using AI as a tactical programmer while you maintain strategic control.

The Strategic vs. Tactical Programmer

Matt's framing for the human-AI relationship in software development:

"Think of AI as a really great on-the-ground programmer — a tactical programmer, a sergeant on the ground making the code changes. You need someone above that, thinking on the strategic level. And that's you."

The strategic level requires software fundamental skills that have been around for 20+ years:

  • Shared design concepts (Brooks) — align with AI before building
  • Ubiquitous language (Evans/DDD) — create a shared vocabulary
  • Software entropy management (Hunt & Thomas) — fight disorder actively
  • Deep modules (Ousterhout) — architecture that AI can navigate and test
  • Test-driven development (Beck) — feedback loops that constrain AI's pace
  • Daily design investment (Beck) — don't divest from code quality

The Skills — Practical Tools

All skills mentioned in the talk are available in Matt's GitHub repo (mattpocock/skills, 13,000+ stars):

  1. Grill Me — adversarial questioning to reach shared design concept before building
  2. Ubiquitous Language — auto-generate a shared vocabulary from your codebase
  3. TDD — force red-green-refactor cycles on the AI
  4. Improve Codebase Architecture — refactor shallow modules into deep modules
  5. Write a PRD — module-aware product requirements with interface specifications

Key Takeaways

  1. Code is not cheap — bad code is the most expensive it's ever been. A hard-to-change codebase prevents you from leveraging AI effectively.
  2. Specs-to-code is vibe coding by another name. Ignoring the code and repeatedly "running the compiler" produces progressively worse results due to software entropy.
  3. Good codebases matter more than ever because AI performs exceptionally well in well-structured code and poorly in messy code.
  4. Reach a shared design concept before building. The "Grill Me" technique (40–100 adversarial questions) prevents the AI from building the wrong thing.
  5. Create a ubiquitous language. A shared vocabulary between you and the AI improves planning quality, reduces verbosity, and aligns implementation with intent.
  6. TDD is essential for AI coding. It forces the LLM to take small steps instead of outrunning its headlights.
  7. Deep modules > shallow modules. AI creates shallow-module codebases by default but can't navigate them. Design for deep modules with simple interfaces.
  8. Design the interface, delegate the implementation. Treat deep modules as gray boxes — test from outside, let AI handle internals.
  9. Invest in system design every day. The difference between success and failure with AI is whether you invest in or divest from your codebase's architecture.
  10. You are the strategic programmer. AI is the tactical sergeant on the ground. The skills needed at the strategic level are decades-old fundamentals that just became more important.
