No Vibes Allowed: Solving Hard Problems in Complex Codebases — Dex Horthy, HumanLayer

Speaker: Dex Horthy — Founder at HumanLayer, author of the "12 Factor Agents" essay that coined the term "Context Engineering"
Event: AI Engineer (December 2025)
Video: YouTube

Introduction — The Problem With AI Coding Today

Dex Horthy opens with a reference to one of the most important studies in AI-assisted software engineering: a survey of 100,000 developers across companies of all sizes, presented at AI Engineer in June 2025. The findings were sobering:

  • Developers using AI coding tools are shipping more code, but a large portion of that output is rework — fixing the "slop" that was shipped the week before.
  • AI works exceptionally well for greenfield projects — a new Vercel dashboard, a fresh React app, a weekend prototype.
  • In brownfield codebases — 10-year-old Java monoliths, mature production systems — AI coding tools can actually make developers less productive.

This matches Dex's personal experience and conversations with founders and senior engineers across the industry. The common refrain: "Too much slop. Tech debt factory. It's just not going to work for our codebase. Maybe someday when the models get better."

But Dex's thesis is that we don't need to wait for better models. The answer is context engineering — the discipline of managing what goes into an LLM's context window to get the best possible output from today's models.

The Breakthrough — From Skeptic to 2–3x Throughput

Dex admits he was initially unimpressed by Claude Code. "It was like, okay, this is a little bit better. I get it. I like the UX." But then his team — just three people — figured something out. Over eight weeks of intense experimentation, they achieved 2–3x more throughput and were shipping so much code that they had to fundamentally change how they collaborated.

The result went viral on Hacker News in September 2025. Thousands of developers grabbed their open-source Research → Plan → Implement prompt system from GitHub. The core goals they backed into:

  1. AI that works in brownfield codebases — not just greenfield toys
  2. Complex problem solving — not just simple changes
  3. No slop — code quality that passes expert review
  4. Mental alignment — keeping the entire team on the same page about how and why the codebase is changing
  5. Maximum token spend — offloading as much meaningful work to AI as possible

Advanced Context Engineering for Coding Agents

The Naive Approach (and Why It Fails)

Dex frames the spectrum of approaches from naive to advanced:

Level 0 — The Argue Loop: Ask the agent to do something. Tell it why it's wrong. Re-steer. Ask again. Repeat until you run out of context, give up, or cry. This is what most people start with.

Level 1 — Fresh Context Windows: Most developers quickly discover that when a conversation goes off track, it's better to start a new context window entirely. Same prompt, same task, but with a fresh start and a note like "don't go down that path, it doesn't work." The signal to restart? When Claude starts apologizing profusely — "that's probably time to start over."

Level 2 — Intentional Compaction: This is the real breakthrough. Whether the conversation is on track or not, you periodically compress your existing context window into a markdown file. You review it, tag it, and when a new agent starts, it can get straight to work instead of re-doing all the file searching, code understanding, and codebase exploration.

What Takes Up Space in Your Context Window

Dex identifies the main context window consumers:

  • File search and discovery — the agent hunting through the codebase
  • Code flow understanding — reading files to understand how things connect
  • File editing — the actual changes
  • Test and build output — often verbose and token-hungry
  • MCP tool output — especially tools dumping JSON with UUIDs into context

A good compaction captures: "This is exactly what we're working on. These are the exact files and line numbers that matter to the problem we're solving."

Why Context Is Everything — LLMs as Stateless Functions

Dex makes a fundamental point about LLM architecture (one that "got him roasted on YouTube"): LLMs are stateless. They're not pure functions because they're nondeterministic, but they have zero memory between calls. The only way to get better output is to put better tokens in.

Every turn of the loop — when Claude picks the next tool call, the next code edit, the next decision — there could be hundreds of right next steps and hundreds of wrong next steps. The only thing that influences which path the model takes is what's currently in the conversation.

This leads to four optimization axes for your context window:

  1. Correctness — no incorrect information (the worst possible contaminant)
  2. Completeness — no missing information the agent needs
  3. Size — minimal noise and irrelevant content
  4. Trajectory — the conversational pattern matters

The Trajectory Trap

The trajectory insight is particularly powerful. If your conversation history looks like: agent makes mistake → human yells → agent makes mistake → human yells — then the LLM is pattern-matching and the most likely next token continuation is… another mistake followed by more yelling. Your conversation history is training data for the current turn.

Inverted priority of what hurts most:

  1. Incorrect information (worst) — sends the model in actively wrong directions
  2. Missing information — the model fills gaps with hallucinations
  3. Too much noise — dilutes signal, wastes smart-zone tokens

The Dumb Zone — A Framework for Context Window Management

Dex introduces what he calls (tongue-in-cheek) a "very academic concept": The Dumb Zone.

Take Claude's ~168,000 token context window. Some tokens are reserved for output and compaction overhead. Around the 40% mark, you start seeing diminishing returns in output quality — depending on task complexity.

The key insight: if you have too many MCP tools loaded in your coding agent, you're doing all your work in the dumb zone and you'll never get good results. The first 40% of context is the "smart zone" — that's where high-quality reasoning happens. Everything after that is increasingly degraded.

Jeff Huntley's research on coding agents puts it succinctly: "The more you use of the context window, the worse outcomes you'll get."

This reframes the entire coding agent workflow: everything is about cleverly avoiding the dumb zone.

Sub-Agents — Not for Roles, for Context Control

Dex has a strong opinion on sub-agents that goes against common practice:

"If you have a front-end sub-agent and a backend sub-agent and a QA sub-agent and a data scientist sub-agent — please stop. Sub-agents are not for anthropomorphizing roles. They are for controlling context."

The correct use of sub-agents: when you need to understand how something works in a large codebase, fork a new context window. That sub-agent does all the reading, searching, file exploration, and codebase understanding. It then returns a succinct summary to the parent agent: "The file you want is here, this is how it works."

The parent agent reads that one file and gets straight to work — without having consumed any of its smart-zone tokens on exploration.

Frequent Intentional Compaction — The Research → Plan → Implement Workflow

The core workflow Dex's team developed is built around constantly keeping the context window small. The entire development process is structured around context management through three phases:

Phase 1: Research

The goal is to understand how the system works: finding the right files, understanding code flow, staying objective. The research phase uses sub-agents to explore the codebase and produces a compressed markdown document that captures:

  • The specific files that matter
  • How the relevant code flows work
  • Dependencies and constraints
  • Exact line numbers and function signatures

This research document is a compression of truth — derived directly from the actual code, not from potentially stale documentation.

Phase 2: Planning

Planning takes the research output plus the bug ticket or feature requirement and creates a detailed implementation plan. The plan includes:

  • Exact steps in order
  • File names and line numbers
  • Actual code snippets of what will change
  • How to test after every change

Dex emphasizes: "If you read one of these plans, you can see very easily how the dumbest model in the world is probably not going to screw this up." The plan is another compaction — compression of intent.

Phase 3: Implementation

With a good plan, implementation is "the least exciting part." The agent simply executes the plan step by step, and the context stays low because all the exploration and decision-making already happened in earlier phases.

Battle Testing — 300,000 Lines of Rust

Dex put Research → Plan → Implement to the test on his podcast with Vibv (CEO of Boundary ML, makers of BAML):

Test 1: One-Shot Fix to a 300K LOC Rust Codebase

Dex attempted to one-shot a fix to BAML's 300,000-line Rust codebase for a programming language. In an hour-and-a-half podcast episode, they:

  • Built research documents (threw some out because they were bad)
  • Made a plan without research and with research, comparing results
  • By Tuesday morning, the CTO had reviewed the PR and confirmed: "Yeah, this looks good. We'll get it in the next release."

Confirmed: works in brownfield codebases. No slop.

Test 2: Complex Problems — 35,000 Lines in 7 Hours

Still skeptical about complex problem solving, Dex and Vibv sat down for a 7-hour Saturday session and shipped 35,000 lines of code to BAML. One of the PRs was merged a week later. (Some of this was codegen — golden file updates when behavior changes — but it was still a massive amount of real work.)

Vibv estimated this represented 1–2 weeks of manual work done in 7 hours.

Test 3: The Limits — Parquet Java and Hadoop

Not everything works. Dex tried to remove Hadoop dependencies from Parquet Java with his friend Blake. It did not go well. At a certain point, they threw everything out and went back to the whiteboard. Once they understood where the footguns were, they had to manually figure out how the pieces fit together.

The critical lesson: "Do not outsource the thinking. AI cannot replace thinking. It can only amplify the thinking you have done — or the lack of thinking you have done."

The Death of "Spec-Driven Development" — Semantic Diffusion

Dex takes a firm stance on the "spec-driven development" hype wave: it's broken. Not the idea, but the phrase itself.

He invokes Martin Fowler's 2006 concept of semantic diffusion: "We come up with a good term with a good definition, then everybody gets excited, everybody starts meaning it to mean a hundred things to a hundred different people, and it becomes useless."

This already happened with "agent" — first a person, then a microservice, then a chatbot, then a workflow, until Simon Willison brought it back to basics: "An agent is just tools in a loop."

Now it's happening to "spec-driven development." Depending on who you ask, it means:

  • Writing a better prompt
  • A product requirements document
  • Verifiable feedback loops with back pressure
  • Treating code like assembly (Sean's original vision)
  • Using a bunch of markdown files while coding
  • Documentation for an open source library (!)

"Spec-driven dev is overhyped. It's useless now. It's semantically diffused."

Four Things That Actually Work Today

Instead of buzzwords, Dex focuses on tactical, practical techniques validated internally and with users:

1. Agent Onboarding — The Memento Problem

Dex references the movie Memento: a man wakes up with no memory and reads his own tattoos to figure out who he is. Every new agent context is that man. If you don't onboard your agents, they will make things up.

Naive approach: Put a massive onboarding document in the root of every repo. Problem: as codebases grow, the onboarding document either gets too long (consuming all your smart-zone tokens just to learn the codebase) or too incomplete (leaving critical information out).

Better approach — Progressive disclosure: Shard the onboarding context down the stack. A file in the root of every repo provides high-level context. At every directory level, additional context files provide deeper information relevant to that specific area. The agent pulls in root context plus only the sub-context relevant to its current task — leaving plenty of room in the smart zone for actual work.

The staleness problem: Internal documentation gets out of date. Every time you ship a new feature, you'd need to validate and rebuild this documentation. Dex draws a provocative chart: between actual code, function names, comments, and documentation, the axis is "the amount of lies you can find" — documentation has the most lies, code has the least.

2. On-Demand Compressed Context (Preferred Over Documentation)

Instead of maintaining documentation, Dex's team prefers on-demand compressed context. When building a feature, you give the research phase a little steering: "We're working in this part of the codebase — SCM providers, Jira, and Linear integration."

The research prompt launches sub-agents that take vertical slices through the codebase and build a research document that is a snapshot of the actually-true, based-on-the-code-itself parts of the codebase that matter. You're compressing truth, not maintaining documentation.

3. Plans With Code Snippets — Compression of Intent

Planning is about compression of intent. Over time, Dex's team iterated toward plans that include actual code snippets of what's going to change.

The goal is threefold:

  • High confidence that the model will do the right thing
  • Compression of intent — a concise representation of what needs to happen
  • Reliable execution — so reliable that even a weaker model could execute it

There's a sweet spot: as plans get longer, reliability goes up but readability goes down. Every team needs to find their own balance point.

Critical warning: This is NOT magic. There is no perfect prompt. The process will not work if you do not read the plan. The entire workflow is built around the human being in back-and-forth with the agent, reviewing plans as they're created. A bad line of code is one bad line. A bad part of a plan could be a hundred bad lines of code. A bad line of research — a misunderstanding of how the system works — could derail everything.

"Watch out for tools that just spew out a bunch of markdown files to make you feel good."

4. Mental Alignment Through Plans and Reviews

Dex asks: "Does anyone know what code review is for?" The answer is mental alignment. Yes, it's about correctness, but the most important function is keeping everyone on the team on the same page about how the codebase is changing and why.

As teams ship 2–3x more code with AI, this becomes critical. Dex can't (and doesn't want to) read thousands of lines of Go every week. But he can read the plans. That's enough to catch problems early and maintain understanding of how the system evolves.

Mitchell Hashimoto's approach: putting AMP threads directly on pull requests so reviewers can see not just a wall of green diffs, but the exact steps, the prompts, and evidence that the build passed. "This takes the reviewer on a journey in a way that a GitHub PR just can't."

Scaling Context Engineering — When to Use What

Dex provides a practical framework for how much context engineering to apply based on task complexity:

  • Trivial change (button color) → Just talk to the agent directly
  • Small feature → Simple plan, maybe skip research
  • Medium feature across multiple repos → One research phase, then build a plan
  • Hard, complex problems → Full Research → Plan → Implement with multiple iterations

The ceiling of what you can solve goes up the more context engineering compaction you're willing to do. But: "It takes reps. You will get it wrong. You have to get it wrong over and over again. Sometimes you'll go too big, sometimes too small. Pick one tool and get some reps."

He explicitly recommends against minmaxing across Claude Code, Codex, Cursor, and other tools — pick one and develop proficiency.

Looking Forward — Cultural Change Is the Hard Part

Dex believes the coding agent techniques themselves will be commoditized. The hard part is the organizational and cultural transformation:

"How do you adapt your team and your workflow and the SDLC to work in a world where 99% of your code is shipped by AI?"

He identifies a growing rift in engineering organizations:

  • Staff engineers don't adopt AI because it doesn't make them that much faster on their already-efficient workflows
  • Junior/mid-level engineers use it heavily because it fills skill gaps — but also produce slop
  • Senior engineers hate it more every week because they're cleaning up AI-generated slop from Cursor the week before

"This is not AI's fault. This is not the mid-level engineer's fault. Cultural change is really hard and it needs to come from the top if it's going to work."

Dex's parting advice for technical leaders: pick one tool and get some reps. The transition to AI-assisted development is inevitable — the question is whether your team navigates it intentionally or gets dragged through it.

Key Takeaways

  1. Context engineering > waiting for better models. You can solve hard problems in complex codebases today by managing your context window carefully.
  2. The Dumb Zone is real. After ~40% of context window utilization, quality degrades. Build your entire workflow around staying in the smart zone.
  3. Sub-agents are for context control, not role play. Use them to explore and compress, not to anthropomorphize job titles.
  4. Frequent Intentional Compaction is the core technique: Research (compress truth) → Plan (compress intent) → Implement (execute with minimal context).
  5. Do not outsource the thinking. AI amplifies thinking — both good thinking and bad thinking. Read the plans. Review the research.
  6. On-demand context beats maintained documentation. Generate fresh, code-based research each time rather than maintaining docs that become lies.
  7. Plans should include code snippets. The more specific your plan, the more reliable execution becomes.
  8. Mental alignment is the point of code review. Use plans and AMP threads to keep your team on the same page as AI-shipped code accelerates.
  9. "Spec-driven dev" is semantically diffused. Focus on the actual techniques (compaction, context management) rather than buzzwords.
  10. Cultural change is the real challenge. The engineering tools will be commoditized; adapting your team and SDLC will not.
