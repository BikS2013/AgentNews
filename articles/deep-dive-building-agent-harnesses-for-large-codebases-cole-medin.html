1 Introduction & The Problem 0:00

Cole Medin opens the video by highlighting a critical gap in the current AI coding ecosystem: while tools like Cursor, Windsurf, and even Claude Code work impressively on small-to-medium projects, they frequently struggle when applied to large, complex codebases. The promise of "vibe coding" falls apart at scale—agents get lost, hallucinate file paths, and produce code that doesn't integrate well with existing architecture.

Anthropic recently published what Cole calls a "masterclass"—a comprehensive guide specifically addressing how to build effective agent harnesses for large codebases. This isn't about making the underlying model smarter; it's about wrapping the model in the right tooling, rules, and context management so it can perform reliably at enterprise scale.

The video is structured around the six core strategies Anthropic outlines, each progressively adding sophistication to how an AI agent interacts with a codebase. Cole emphasizes that these strategies aren't theoretical—they're immediately applicable and he's already built a plugin implementing many of them.

Core insight: The biggest bottleneck to AI coding at scale isn't model intelligence—it's how you structure the context and tooling around the model.
  • AI coding tools hit a wall with codebases beyond ~50K lines of code
  • Anthropic published a detailed guide focused specifically on large codebase challenges
  • Six strategies are presented, from simple to advanced
  • The guide is model-agnostic in principle but demonstrated via Claude Code

2 How Claude Code Navigates Codebases 1:52

A key revelation in the video is how Claude Code actually navigates large codebases. Unlike what many assume, it does not use RAG (Retrieval-Augmented Generation), pre-built indexes, or embeddings. Instead, Claude Code uses an entirely agentic approach to search—it reads files, searches for symbols, navigates directories, and explores the codebase step by step, much like a human developer would.

This agentic search approach has both strengths and limitations. On the positive side, it means Claude Code doesn't require any pre-processing, indexing, or infrastructure setup—you just point it at a repo and it starts working. However, the downside is that without proper guidance, the agent can waste significant tokens (and time) exploring irrelevant parts of the codebase.

Cole explains that this architectural choice is precisely why the harness strategies matter so much. If the agent is searching agentically, then giving it better starting context, maps of the codebase, and scoped rules dramatically improves both the speed and accuracy of its work. The harness essentially gives the agent a "cheat sheet" so it doesn't have to discover everything from scratch on every task.

  • No RAG or embeddings: Claude Code searches codebases agentically at runtime
  • No pre-indexing: Works immediately without setup infrastructure
  • Agentic search tools: Uses grep, file reading, directory listing, and symbol search
  • Better context upfront = fewer wasted tokens and faster results
  • This approach makes the harness/context layer critical for large repos

Anthropic's guide emphasizes that the "AI layer"—the harness of tools, rules, context, and integrations wrapped around the LLM—matters more than the underlying model itself. A well-configured harness with a good model will dramatically outperform a frontier model with no harness.

The practical implication is significant: teams should invest as much (or more) effort into configuring their agent harness as they do into prompt engineering. This means maintaining claude.md files, setting up hooks, creating codebase maps, and configuring MCP servers—all of which are explored in the subsequent strategies.

Key principle: "The harness matters more than the model." A Sonnet-class model in a well-built harness outperforms Opus with no harness on large codebases.

4 Strategy 1: Lean & Layered Global Rules 4:47

The first and most foundational strategy is creating lean, layered rules using claude.md files. These files serve as the system prompt or instruction set that Claude Code reads before working on your codebase. The key word here is "lean"—Anthropic explicitly warns against bloated rule files that try to cover every edge case. Instead, rules should be concise, actionable, and structured.

The layering aspect is what makes this strategy powerful at scale. You place a root-level claude.md at the project root with global conventions (coding style, commit message format, testing requirements). Then, at 5:42, Cole explains how subdirectory-scoped claude.md files override or extend the root rules for specific parts of the codebase. A frontend/claude.md might specify React conventions while backend/claude.md specifies API patterns.

This hierarchical approach mirrors how large engineering teams actually work—global standards with team-specific conventions. The agent automatically picks up the relevant rules based on which files it's working with, ensuring it follows the right patterns without being overwhelmed by irrelevant information.

Cole emphasizes that rules should be treated like code: version-controlled, reviewed in PRs, and iterated on continuously. When the agent makes a recurring mistake, the fix isn't to yell at it in the prompt—it's to add a rule to the appropriate claude.md file.

Anti-pattern: Stuffing everything into one massive rules file. Keep it lean—under 500 lines for root, and scope specifics to subdirectories.
  • claude.md at project root for global rules and coding standards
  • Subdirectory claude.md files for team/module-specific conventions
  • Rules should be lean, actionable, and version-controlled
  • Scoping at 10:20 — test and lint configurations should be scoped per directory
  • Treat rules like code: iterate, review, and refine over time

5 Strategy 2: Codebase Maps 7:39

The second strategy addresses one of the biggest challenges agents face in large codebases: knowing where things are. A codebase map is essentially a high-level directory structure document that describes the purpose and contents of each major directory and key file in the project. Think of it as a README specifically written for the AI agent.

Cole explains that this map goes beyond a simple tree command output. It should include semantic descriptions: not just that src/services/ exists, but that it contains "business logic services for user authentication, payment processing, and notification dispatch." This semantic layer helps the agent make intelligent decisions about where to look for existing code and where to place new code.

The codebase map is typically placed in the root claude.md or in a dedicated file referenced from it. For very large monorepos, each major package or service can have its own map. The key insight is that a few hundred tokens of map information can save thousands of tokens of agentic search, making the agent both faster and more accurate.

Anthropic recommends keeping these maps updated as part of your regular development process. When new directories are added or major refactors happen, the map should be updated alongside the code changes. Some teams even automate map generation as part of their CI pipeline.

  • A codebase map is a semantic directory structure document
  • Goes beyond tree output—includes purpose descriptions for each area
  • Dramatically reduces wasted agentic search tokens
  • Can be placed in root claude.md or a separate referenced file
  • Should be maintained alongside code changes, possibly automated via CI

6 Strategy 3: Self-Improving Hooks 10:47

Hooks are one of the most powerful and underutilized features covered in the video. Claude Code supports lifecycle hooks—scripts that run automatically at defined points during the agent's execution. The two primary hooks discussed are stop hooks (run when the agent finishes a task) and start hooks (run when the agent begins a new task).

At 11:17, Cole demonstrates a stop hook that automatically runs linting, type checking, and tests after the agent completes its work. If any checks fail, the hook feeds the errors back to the agent so it can fix them—creating a self-correcting loop. This is similar to how a senior developer would review and fix their own work before submitting a PR.

The start hook, demonstrated at 12:18, is even more interesting. It can load relevant context, recent git changes, or previously learned lessons before the agent begins work. Cole shows how a start hook can read from a "lessons learned" file, giving the agent memory across sessions—essentially making it smarter over time.

At 13:35, Cole discusses the self-reflection process: when the agent encounters and fixes an error, a hook can append the lesson to a knowledge base. The next time the agent starts, it reads these lessons. Over time, the agent accumulates project-specific knowledge, effectively becoming a specialist in your codebase.

Self-improvement loop: Stop hook catches errors → Agent fixes them → Lesson is logged → Start hook loads lessons next session → Agent avoids repeating the mistake.
  • Stop hooks: Run linting, tests, and type checks automatically after completion
  • Start hooks: Load context, recent changes, and learned lessons
  • Self-reflection: Agents can log lessons from errors for future sessions
  • Creates a continuously improving agent experience per-project
  • Hooks are configured in Claude Code's settings and are fully customizable

7 Strategy 4: Scoped Skills 15:23

Skills represent a more sophisticated evolution of the rules concept. While claude.md files provide always-on context, skills are loaded on-demand based on what the agent is doing. This implements what Cole calls "progressive disclosure"—the agent only receives the detailed instructions it needs for the specific task at hand, keeping its context window lean and focused.

Skills are defined as markdown files that describe how to perform specific operations. For example, you might have a skill for "creating a new API endpoint," another for "adding a database migration," and another for "setting up a new React component." Each skill contains step-by-step instructions, conventions, and examples specific to your project.

The critical innovation is path scoping: skills are associated with specific file paths or glob patterns. A skill for API endpoint creation activates only when the agent is working in the backend/routes/ directory. This prevents context pollution—the agent working on frontend code never sees backend-specific skills.

At 16:46, Cole clarifies the distinction between skills and rules. Rules (in claude.md) are always loaded and describe general conventions. Skills are conditionally loaded and describe specific workflows. Rules say "use TypeScript strict mode"; skills say "here's the exact 12-step process for adding a new service endpoint."

  • Progressive disclosure: Load instructions only when relevant
  • Path-scoped: Skills activate based on which files the agent is working with
  • Defined as markdown files with step-by-step procedures
  • Keeps context window lean—agent only sees what it needs
  • Rules vs Skills: Rules = always-on conventions; Skills = on-demand workflows

8 Strategy 5: LSP + MCP Servers 17:42

The fifth strategy brings IDE-grade intelligence to the agent through the Language Server Protocol (LSP) and Model Context Protocol (MCP) servers. LSP gives the agent access to the same symbol-level code intelligence that powers features like "Go to Definition," "Find References," and "Rename Symbol" in your IDE. This is a game-changer for large codebases where understanding code relationships is critical.

At 19:10, Cole demonstrates a custom MCP server that exposes LSP capabilities to Claude Code. Instead of the agent having to grep for function names and guess at import chains, it can directly query "find all references to this function" or "what's the type signature of this class." This dramatically reduces hallucination and improves the agent's understanding of code structure.

Cole explains at 20:29 why this matters especially for large codebases: when you have hundreds of files with similar naming patterns, grep-based search produces too many false positives. LSP provides semantic understanding—it knows the difference between a function definition, a function call, and a comment that mentions the function name.

The MCP server acts as a bridge, translating LSP capabilities into tools that Claude Code can call. This means you can create custom MCP servers that expose project-specific tooling—database schema queries, API documentation lookups, dependency graph traversals—anything that helps the agent understand your specific codebase better.

LSP advantage: Semantic code understanding vs. text-based search. The agent can follow type hierarchies, call chains, and import graphs with precision.
  • LSP integration: Symbol search, go-to-definition, find-references for agents
  • MCP servers: Custom tool bridges exposing any capability to the agent
  • Eliminates grep-based false positives in large codebases
  • Provides semantic understanding of code relationships
  • Can expose project-specific tools: DB schema, API docs, dependency graphs

9 Strategy 6: Sub-Agents 21:57

The final and most advanced strategy is the use of sub-agents—spawning specialized child agents for different phases of a task. The key insight from Anthropic is to separate exploration from editing. One agent explores the codebase, gathers context, and builds a plan; another agent takes that plan and executes the actual code changes.

This separation addresses a fundamental problem: exploration and editing require different modes of operation. An exploring agent needs broad access and should read many files without modifying anything. An editing agent needs focused context and precise instructions. Combining both in one agent leads to context window bloat and confused behavior.

Cole explains that sub-agents can be configured with different tools, permissions, and even different models. The exploration agent might use a cheaper, faster model since it's just reading and summarizing. The editing agent might use a more capable model since precision matters for code changes. Each sub-agent gets its own context window, effectively multiplying the available context.

In practice, this pattern looks like: a main orchestrator agent receives a task, spawns an explorer sub-agent that reads relevant files and produces a summary/plan, then spawns an editor sub-agent with that focused plan to make changes. The orchestrator can then spawn a reviewer sub-agent to validate the changes—creating a multi-agent review pipeline.

  • Separate exploration from editing: Different agents for different phases
  • Each sub-agent gets its own clean context window
  • Can use different models for different sub-agents (cost optimization)
  • Orchestrator pattern: explore → plan → edit → review
  • Effectively multiplies available context for complex tasks

11 Organizational Adoption 25:54

The final strategic section covers Anthropic's advice on rolling out agent harnesses across engineering organizations. This isn't just a technical challenge—it's an organizational change management challenge. Anthropic recommends starting with a small group of enthusiastic early adopters, letting them build and refine the harness configuration, and then gradually expanding to more teams.

A critical recommendation is to make the AI layer a shared, maintained artifact—not something individual developers configure on their own machines. The claude.md files, skills, hooks, and MCP configurations should all live in the repository and be reviewed like any other code. This ensures consistency and allows the entire team to benefit from improvements.

Cole highlights that Anthropic suggests designating "AI champions" or "harness maintainers" on each team—people who take ownership of refining the agent configuration based on feedback from their teammates. These maintainers collect common failure patterns and translate them into rules, skills, or hooks that prevent the failures from recurring.

The end goal is a flywheel effect: as the harness improves, developers use the agent more; as they use it more, they discover more edge cases; those edge cases get codified into better harness configuration; which makes the agent even more reliable. Over time, the organization builds a highly customized, deeply knowledgeable AI assistant tuned specifically for their codebase.

Flywheel: Better harness → More usage → More edge case discovery → Better harness → Even more reliable AI assistance.
  • Start with enthusiastic early adopters, expand gradually
  • AI layer configuration should live in the repo and be version-controlled
  • Designate "AI champions" or harness maintainers per team
  • Collect failure patterns and codify them into rules/skills/hooks
  • Goal: a self-improving flywheel of AI capability
