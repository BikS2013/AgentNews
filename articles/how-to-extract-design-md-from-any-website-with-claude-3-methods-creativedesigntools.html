Overview

CreativeDesignTools delivers an exhaustive, hands-on tutorial on extracting DESIGN.md files — Google's open-source design token specification — from any website using three progressive methods. From screenshot-based extraction with carefully crafted prompts, to running a JavaScript style-auditing script in DevTools, to fully automated Claude Code/Co-Work workflows, each method builds on the previous one. The video emphasizes review, validation, and understanding over blind AI trust — teaching you to catch AI hallucinations, validate with Google's linter, inspect computed styles in DevTools, and produce production-ready design files plus Tailwind configs.

1 What Is DESIGN.md & Why It Matters ▶ 0:00

The DESIGN.md file is a structured design token specification open-sourced by Google. It captures a website's entire visual identity — colors, typography, spacing, elevation, motion — in a single markdown file that any AI or developer can consume.

  • Production-ready output — by the end of each method, you get a DESIGN.md file plus a Tailwind config you can drop straight into a project
  • Three progressive methods — screenshot extraction, computed style script, and Claude Code/Co-Work automation. Each builds on the previous.
  • Don't skip ahead — the methods are deliberately ordered so you learn to detect errors and validate AI output before automating

2 Resources — Where to Find DESIGN.md Files ▶ 1:47

Two key resources for understanding and finding DESIGN.md files:

  • Google's open-source GitHub — the official architecture and structure specification. This is the reference every prompt should point to.
  • getdesign.md — a community library of pre-extracted DESIGN.md files for major brands (BMW, HP, Airbnb, Airtable, AOL, etc.). Useful for reference but may be outdated — always verify against the live site.

3 Method 1 — Screenshot Extraction ▶ 3:38

The first method works from screenshots only — no access to the live site required. You capture key screens and feed them as context to Claude.

  • What to capture — the main landing/home page, a secondary page with different components, and optionally logged-in dashboard views (sometimes uses a different design system)
  • Three screenshot files — attach them as context to the AI prompt
  • Limitation — AI is "guessing from pixels." Colors may be approximate, motion/animation values are always inferred, and there's no way to know CSS variable names.
  • Best for — competitor analysis, design inspiration, sites you can't access programmatically

4 The Extraction Prompt — Anatomy & Hard Rules ▶ 8:23

A carefully structured prompt is the key to production-quality output on the first try. The prompt has several critical sections:

  • Reference URLs — point to Google's open-source DESIGN.md spec, the README, and example files. This gives AI a strict structural reference.
  • Structure order — branding, colors, typography, layout, spacing — matching Google's canonical order
  • Hard rules — (1) mirror the exact layout of the reference, (2) capture the full design system spirit, (3) use real hex values from the source, (4) use an comment for values the AI isn't confident about
  • The uncertain flag — forces AI to mark guesses explicitly, dramatically reducing silent hallucination. You can then search for "uncertain" in the output and review each one manually.
  • Single file output — instruct the AI to produce exactly one DESIGN.md file, nothing else
Key insight: "The uncertain comment forces the AI to flag values it's not sure about. This reduces hallucination because the AI will mark guesses explicitly instead of inventing values silently."

5 Reviewing AI Output — Catching Mistakes ▶ 14:20

The review step is critical. AI can silently "fix" or "invent" values that look reasonable but aren't what you want.

  • Check dos and don'ts — make sure they're specific to YOUR design (e.g., "keep cards on white with soft purple-tinted shadows"), not generic boilerplate
  • AI "fixing" things — example: a design had "walk, play, play" labels but the AI changed the third to "distance" because the metric was in kilometers. The AI was being smart, but it changed the designer's intent.
  • Three categories of AI changes — ask yourself: did it (1) change something, (2) fix something, or (3) invent something? Then decide if you want to keep it.
  • Motion values are ALWAYS inferred — there's no way AI can detect animations from screenshots. Easing, duration, and timing values come from Material 3 defaults, not from the actual source.
  • Search for "uncertain" — review all 8+ flagged items one by one against the original screenshots
Key insight: "Every time you spot something the AI outputs that doesn't seem right, ask yourself: did it change something, fix something, or invent something?"

6 Validation with Google's DESIGN.md Linter ▶ 19:52

Google provides an official linter for DESIGN.md files that validates structure and catches errors.

  • Install — npx design-lint path/to/DESIGN.md
  • Output — reports errors (structural problems) and warnings (style suggestions). Aim for zero errors.
  • Why it matters — ensures your file follows the canonical structure, making it compatible with any tool that consumes DESIGN.md files
  • After each method — always run the linter as a final validation step

7 Method 2 — Computed Styles from Live Websites ▶ 22:45

The second method reads the actual computed styles from a live website's browser rendering. No guessing — these are the real values the browser uses.

  • Computed style — the final, resolved CSS value after all stylesheets, variables, and inheritance are applied. If a button uses var(--primary-color), the computed style is the actual hex value like #3b82f6.
  • Why this is better than screenshots — exact hex values, real font sizes, actual CSS variable names, border radii, spacing — all deterministic, no pixel guessing
  • Source material — Awwwards nominees, competitor sites, any production website you can open in your browser
  • The script runs client-side only — it reads from the DOM, doesn't send anything to any server, doesn't install anything. Purely read-only diagnostic.
Key insight: "The previous method relies on AI guessing from pixels. This method actually reads the computed styles from the browser. There's no guessing."

8 The Style-Auditing Script — Deep Walkthrough ▶ 27:54

A JavaScript script that runs in the browser's DevTools console. It walks every visible element on the page and extracts the full design system into a JSON object.

  • Step 1 — Constants & helpers — filters out browser default colors (unvisited link blue, visited link purple, transparent) to avoid noise in the output
  • Step 2 — CSS variables — walks every stylesheet (including cross-domain), pulls all CSS variables (--primary-color, --brand-accent, etc.)
  • Step 3 — Filter & categorize — separates variables into colors and brand-meaningful names using regex patterns
  • Step 4 — Keyframes & animations — captures animation variable names to understand team intent
  • Step 5 — Element walk — visits up to 4,000 visible elements, extracting color, background, border, border-radius, font family, weight, spacing for each. Groups results into 7 buckets (text colors, background colors, border colors, SVG fills, font families, font sizes, font weights)
  • Step 6 — Frequency count & JSON output — sorts by usage frequency. The most-used values in each bucket define the brand. Outputs grouped key-value JSON.
  • Security — always verify scripts before running in your browser. Ask an AI "is this script safe to run?" and paste the code. This script is purely read-only.
  • 4,000 element cap — configurable. Bump to 6,000-10,000 for very large websites to avoid missing elements.
Key insight: "The most used values in each bucket is usually what defines the brand. A color used as text means something different than the color used as a button background — that's why we have 7 separate buckets."

9 Turning JSON Results into a DESIGN.md ▶ 42:01

With the JSON output from the script, you feed it to Claude with a specialized prompt to generate the DESIGN.md file.

  • The prompt — specify the URL, brand name, attach the JSON results, and reference Google's DESIGN.md spec. Customize URL and brand name for each extraction.
  • Hard rules for this method — (1) any color appearing fewer than 3 times gets a "low confidence — verify on live site" comment, (2) for each color, add a one-line comment citing frequency evidence
  • Why frequency matters — forces AI to justify its semantic role assignments. A color used 2,340 times is likely primary; a color used 3 times might be noise from an SVG icon.
  • Dual design systems — the Vercel example revealed two naming conventions (geist and ds) coexisting, possibly from a migration. The AI recognized and handled both.
  • Result structure — colors organized in tiers (surface, foreground, text, inverse, outline, primary), each with frequency-based reasoning comments. Then typography, rounded corners, spacing, components — all following Google's canonical architecture.

10 Non-Determinism — Why Outputs Differ ▶ 51:07

Extracting DESIGN.md is inherently non-deterministic and open to interpretation. Different methods produce different (but not necessarily wrong) results.

  • Library vs. reality — getdesign.md showed Vercel with a white background; the live site is dark mode black. Libraries capture snapshots that may be outdated.
  • "Almost white" vs. "pure white" — the script extracted the primary foreground as almost-white (#FAFAFA), not pure white (#FFFFFF). Both are "right" in different contexts.
  • Declared but unused tokens — some CSS variables exist in stylesheets but are never rendered. They show up in the extraction but aren't part of the visual design.
  • Don't assume AI is wrong — when Claude generates a value that seems off, investigate before correcting. The "wrong" value may be the actual computed style.
Key insight: "Extracting a DESIGN.md is non-deterministic and open to interpretation. We don't know how the designers are thinking — all we have to work with is the trails they left behind in their code."

11 DevTools Verification — The Source of Truth ▶ 54:34

The browser's DevTools Computed tab is the deterministic source of truth. The video walks through inspecting real elements on Vercel's website.

  • Open DevTools — right-click → Inspect, or Cmd+Option+J (Mac)
  • Elements tab — hover over code to highlight elements, or use the selector tool to click on any element in the page
  • Computed tab — shows the actual rendered values (not declared CSS). Use this over the Styles tab for verification.
  • What to check — background-color, border-radius (e.g., 100px = pill shape), height (e.g., 40px for CTA buttons), font properties
  • Practical tip — the console panel can hide the Elements panel. Drag the divider down if you can't see the code. Click the Elements tab (not Console) when inspecting.
  • Verification confirmed — the CTA button's background color matched what Claude Code generated, proving the extraction was correct

12 Fluid Typography — Why Sizes Don't Match ▶ 1:00:00

A common gotcha: the script reports a font size of 48px, but DevTools shows a different value. The reason is fluid (responsive) typography.

  • Fluid typography — font sizes change based on viewport width using clamp() or CSS calculations. The "48px" is one possible value at one viewport size.
  • Resize to see it change — dragging the browser window shows the font-size updating in real-time in the Computed tab
  • Fixed vs. fluid tokens — the DESIGN.md prompt should distinguish between fixed tokens (e.g., 14px body text) and fluid tokens (e.g., heading that scales with viewport)
  • Why this matters for DESIGN.md — if you record only "48px" you miss the responsive behavior. The prompt's hard rules instruct AI to identify and label fluid typography separately.
Key insight: "The font size in our JSON script said 48px, but DevTools shows a different value. That's because Vercel uses fluid typography — the size changes based on your viewport."

🎯 Key Takeaways

  1. DESIGN.md is Google's open-source design token spec — a single markdown file capturing colors, typography, spacing, motion, and elevation for any design system. Drop it into any AI workflow.
  2. Three progressive methods — (1) screenshot extraction for when you only have images, (2) computed style script for live websites with exact values, (3) Claude Code/Co-Work for full automation. Learn them in order.
  3. The "uncertain" comment trick — instruct AI to flag values it's not confident about with <!-- uncertain -->. Then search for those flags and review each one manually. Dramatically reduces silent hallucination.
  4. Motion values are always inferred from screenshots — AI cannot detect animations from static images. Easing, duration, and timing values are borrowed from Material 3 defaults, not from the source.
  5. AI will silently "fix" things — it might rename labels, correct perceived errors, or adjust values based on reasoning. Always ask: did it change, fix, or invent? Then decide if you keep it.
  6. Frequency-based color assignment — the computed style script counts how many times each color appears. Colors used 2,000+ times are likely primary; colors used fewer than 3 times are probably noise.
  7. DevTools Computed tab is the source of truth — the deterministic way to verify any value. Use it to check what the browser actually renders, not what the stylesheet declares.
  8. Watch for fluid typography — a font size of "48px" from the script may be one value in a responsive clamp() function. The actual size changes with viewport width.
  9. Always validate with Google's linter — npx design-lint DESIGN.md catches structural errors and ensures compatibility with the ecosystem.
  10. Production websites have messy realities — dual design systems (migration leftovers), declared-but-unused tokens, outdated library entries. Your extraction tools must handle these gracefully.
  11. The Tailwind config is a bonus deliverable — the extraction process produces both DESIGN.md and a ready-to-merge Tailwind JSON config with all tokens mapped.
  12. Learn the process before automating — "once you know the process, AI becomes a multiplier. You'll trust it more and you'll be able to work way faster."
