Overview

Mark Kashef tackles a problem nobody's talking about: when developers switch between Claude Code and Codex, their skills don't transfer. The way skills are designed, structured, and executed differs between providers — meaning you end up recreating skills from scratch every time you switch. His solution is PolySkill, a universal adapter that converts any skill to work in both Claude Code and Codex (and back) with a single command. The video covers the anatomy of skills in both runtimes, the key structural differences, and a live demo of two-way skill conversion.

1 The Skill Portability Problem ▶ 0:00

The Claude Code vs Codex debate keeps swinging back and forth — Claude Code was everyone's darling a few months ago, then Codex emerged and people flocked over. Mark expects this trend to continue oscillating. But the real problem nobody's discussing: when you switch providers, your skills don't come with you.

Both providers can handle skills, but the way they're designed, used, and executed is fundamentally different. You end up recycling and recreating skills over and over again.

Goal: one universal adapter — a single skill that converts Claude Code skills to Codex skills and vice versa, keeping you nimble in this ever-changing landscape.

2 Why the Same Skill Behaves Differently ▶ 1:34

Although the overall concept of a skill is the same between OpenAI and Anthropic, the mechanics differ in important ways:

  • Claude Code: You can drop terminal commands directly in the middle of a skill body using backtick-bang syntax (`!), and it knows how and when to execute them. It reads all skill descriptions as-is into the context window at session start (under a character limit).
  • Codex: Has a description cap — if you have too many skills, it may not read the full description of each one. Triggers at the end of a description may never be seen. Also has an extra sidecar YAML file for configuration (tools, services, display settings, policies, invocation rules) that doesn't exist in Claude Code.
Practical tip for Codex: put your trigger conditions at the beginning of the description, not the end — they might get cut off.

3 Anatomy of an Agent Skill ▶ 3:27

The generic anatomy of an agent skill across both providers:

  • skill.md — the main file with name, description, and markdown body (commands, context, order of operations)
  • Scripts/ — Python scripts the agent can execute
  • References/ — additional reference files the skill can refer to
  • Assets/ — additional assets referenced from the skill body

Claude Code specifics ▶ 4:07:

  • Name in kebab-case
  • allowed-tools — which bash commands the skill can execute
  • disable-model-invocation — run autonomously or require user approval each time
  • Dynamic injection via backtick-bang (`!command`) — terminal commands embedded inline in the skill body

Codex specifics ▶ 5:04:

  • Short description under a metadata heading
  • Sidecar YAML file — display settings, icon, default prompt, tool dependencies, policies, invocation rules
  • Functionally similar capabilities, but different structural requirements

4 How PolySkill Works ▶ 5:59

PolySkill is built around three core pieces, designed like a universal travel adapter:

  1. Shared Structure (definition.md) — A neutral, provider-agnostic version of what each skill needs. Identifies what the skill does irrespective of syntax specifics.
  2. Adapters (cartridges) — Plug-in modules for each provider. Plug a cartridge in → that tool is supported. Pull it out → no longer available. If Gemini becomes competitive, you'd just create a new adapter cartridge.
  3. CLI interface — Natural language commands to convert and install skills across providers.
Future-proof by design: if a new runtime appears (Gemini, GPT-5.7, Opus-5.5), you just analyze its skill schema and create a new adapter cartridge — no need to rebuild the entire system.

5 Installation & Usage ▶ 7:22

The workflow is three stages:

  1. Bring the skill — place the skill and associated assets in the provider's skills folder
  2. polyskill install — builds the skill, then installs it globally for both providers (Claude Code at ~ level, Codex at .agents level)
  3. /polyskill convert [skill-name] to [provider] — converts any skill to work in the target provider (or $polyskill in Codex CLI)

Once installed, the skill shows up in both Claude Code (via / slash command) and Codex (via $ command or the Codex app).

  1. Skill portability is a real problem. Claude Code and Codex skills look similar conceptually but differ structurally — you can't just copy them across.
  2. Claude Code uses backtick-bang for inline commands; Codex uses a sidecar YAML for configuration — fundamentally different execution models.
  3. Codex has a description cap. Put triggers at the beginning of skill descriptions, not the end, or they may get cut off.
