Overview

Perplexity has open-sourced Bumblebee, a read-only scanner that inventories every package, editor extension, browser extension, and AI tool config on a developer's machine — without running package managers or executing project code. In this hands-on walkthrough, Better Stack installs Bumblebee, runs it live, and breaks down its three scan profiles (baseline, project, and deep/incident response), its NDJSON output format, and why a read-only approach matters during supply chain incidents. The video covers what makes Bumblebee different from SCA tools, SBOM generators, and EDR solutions, and explains exactly when and how developers should integrate it into their security workflow.

1 The Dev Machine Supply Chain Problem ▶ 0:00

When a supply chain attack drops, the question isn't "is production safe?" — it's "did anyone install this thing locally?" The old security model was simple: scan the repo, scan the container, scan production. But that no longer reflects how developers actually work.

Today, a single developer laptop can have:

  • Multiple package managers — npm, pip, Go modules, Bun, etc.
  • Browser extensions — Chrome, Firefox add-ons with broad permissions
  • Editor extensions — VS Code, Cursor plugins
  • AI coding tools — Claude, Copilot, local agents
  • MCP configs — model context protocol server configurations
That is a lot of trust packed into one machine. And it's the part your existing security stack probably doesn't see clearly.

2 What Is Bumblebee ▶ 0:35

Perplexity built Bumblebee internally for exactly this problem, then open-sourced it. It's a read-only, single binary scanner that inventories packages, editor extensions, browser extensions, and AI tool configs from local metadata.

Key design principles:

  • No npm ls — doesn't call package managers
  • No pip show — doesn't import any Python packages
  • No project code execution — doesn't build your Go project
  • Metadata only — reads file system metadata, nothing else
Bumblebee reads metadata, emits inventory, matches known exposures, and gets out. That's the entire design philosophy.

3 Install & Self-Test ▶ 1:25

Installation is a single Go install command from GitHub. That gives you a single Go binary — no daemon, no service, nothing running in the background.

# Install Bumblebee go install github.com/perplexityai/bumblebee@latest # Run self-test to verify installation bumblebee self-test # Expected output: "self-test okay"

The self-test confirms the scanner can detect its known fixture data correctly. If you get "self-test okay," you're ready to scan.

4 Running a Baseline Scan ▶ 1:55

The baseline scan is the standard developer endpoint inventory. It checks common global and user-level package roots, editor extensions, browser extensions, and supported MCP configs.

# Run a baseline scan and output to NDJSON file bumblebee scan --profile baseline > scan-results.ndjson

This is the scan you'd use for regular recurring checks — "what normally exists on this developer machine?" is the question it answers.

5 Reading the NDJSON Output ▶ 2:15

Each line in the output is a structured JSON record containing:

  • Ecosystem — which package ecosystem (npm, PyPI, Go, etc.)
  • Package name — the exact package or extension identifier
  • Version — currently installed version
  • Source file — where Bumblebee found the metadata
  • Confidence level — how certain the detection is
  • Location metadata — the full path on disk

Because it's NDJSON (newline-delimited JSON), you can pipe it into jq, ship it to a file, collect it through MDM, ingest it into a SIEM, or hand it to another agentic workflow. It's designed to be boring, scriptable infrastructure.

# View the first few results head scan-results.ndjson # Filter for npm packages only cat scan-results.ndjson | jq 'select(.ecosystem == "npm")' # Search for a specific package cat scan-results.ndjson | jq 'select(.name == "suspicious-package")'
Instead of asking "do I maybe have this installed somewhere on the system?" — you can now actually see it right there in structured data.

6 Why Bumblebee Is Not Another SCA Tool ▶ 3:00

At first glance, Bumblebee might look like just another security scanner. But it occupies a different niche entirely:

  • SCA tools — focus on your application dependencies (what your project uses)
  • SBOM tools — focus on what you shipped (what's in the artifact)
  • EDR — focus on what you executed (runtime behavior)
  • Bumblebee — focuses on the local developer state (what's present on the machine)

The critical scenario: a compromised package advisory drops. You need to know which laptops might be exposed. The obvious move is to ask everyone to run package manager commands — but that's exactly the wrong thing. If you're looking for something malicious, you don't want your investigation command to accidentally execute the malicious behavior (lifecycle scripts, plugin hooks, etc.).

Bumblebee's approach: read metadata, emit inventory, match known exposures, then get out. No execution, no risk of triggering the very thing you're investigating.

7 Baseline vs Project vs Deep Scan Profiles ▶ 3:54

Bumblebee ships with three scan profiles, each designed for a different use case:

  • Baseline — lightweight recurring scan. Looks at global packages, user-level toolchains, extensions, and MCP configs. Answer: "What normally exists on this developer machine?"
  • Project — scans known workspace directories (~/code, ~/source, ~/work). Use this when you care about lock files across actual dev folders.
  • Deep — incident response mode. You point it at explicit roots (even something broad like ~), usually with an exposure catalog and a duration limit.
# Normal workflow: baseline when things are calm bumblebee scan --profile baseline > baseline.ndjson # When something bad happens: switch to deep scan bumblebee scan --profile deep --root /home/user > deep-scan.ndjson
Baseline when things are calm. Deep scan when there's smoke. That's the entire operational model.

8 What Bumblebee Scans ▶ 4:55

The coverage is what makes Bumblebee genuinely interesting. It can scan across:

  • Package managers — npm, pnpm, Yarn, Bun, Go modules, PyPI, and more
  • Editor extensions — VS Code, Cursor extensions
  • Browser extensions — Chrome, Firefox, etc.
  • MCP JSON configs — this is a major feature because MCP configs are becoming the new .env files, scattered across developer machines

Technical specs:

  • Single Go binary with zero non-standard library dependencies
  • Fast — metadata-only scanning completes in seconds
  • Outputs NDJSON — pipeable into jq, MDM, SIEM, or agentic workflows
  • Open source — MIT licensed

9 Why Read-Only Scanning Matters ▶ 5:30

The read-only approach is not a minor detail — it's the core safety property. During a supply chain incident, the advice "just run the package manager and see what happens" can be dangerous. If the package you're investigating has malicious lifecycle scripts or weird plugin behavior, your scanner could accidentally trigger the very exploit you're looking for.

Bumblebee fills a real gap in the security stack:

  • CI/CD — most teams have some visibility here
  • Container/production — usually covered by existing tools
  • Developer machines — this is the messy part that Bumblebee addresses

Dev machines have half-finished projects, old clones, global packages, test virtual environments, AI tooling — all the stuff that never shows up in your clean official inventory. Bumblebee gives you a practical way to see that local state.

The AI config coverage is right on time. Local agents, MCP servers, and tool-calling workflows are moving fast, and MCP configs are becoming the new .env files across developer machines.

10 Should Developers Use Bumblebee? ▶ 7:20

The answer is yes, especially if your day-to-day work touches npm, Go, VS Code, Cursor, Claude, MCP servers, or similar tools. The recommended workflow:

  1. Run a baseline scan once a week — one single command gives you a snapshot of what's on your machine
  2. Dump the NDJSON to a central location — archive results for searchability
  3. When an incident hits — search across everything instead of asking everyone in Slack "Hey, does anyone have this?"
# Weekly baseline scan (add to cron) bumblebee scan --profile baseline > ~/scans/$(date +%Y-%m-%d)-baseline.ndjson

Current limitations to keep in mind:

  • Brand new — just dropped, expect changes and rapid iteration
  • macOS and Linux only — no Windows support yet
  • Depends on advisory data — the exposure catalog flow gets much more useful when you have good advisory data to match against
  • Not EDR — answers a narrower question: "What packages, extensions, and dev tool configs are present on this machine? Do any match something we know is bad?"
Bumblebee tells you which dev machines are currently exposed through local package metadata, extension manifests, and supported AI tool configs. That is extremely useful in the first hour when anything goes wrong — nobody wants to debate, they want to know who is exposed, where is it, and how fast to prove it.

🎯 Key Takeaways

  1. Developer machines are the blind spot — traditional security tools cover CI/CD, containers, and production, but dev laptops with their package managers, extensions, and AI tools are largely invisible
  2. Bumblebee is a read-only scanner — it reads file system metadata only, never executing package managers, importing packages, or running project code
  3. Not another SCA tool — SCA covers app dependencies, SBOM covers shipped artifacts, EDR covers execution; Bumblebee covers local developer state
  4. Three scan profiles for different contexts — baseline for weekly checks, project for workspace-level auditing, deep for incident response
  5. NDJSON output is deliberately boring — pipe into jq, ship to MDM, ingest into SIEM, or feed to agentic workflows. Scriptable infrastructure by design
  6. MCP config scanning is a killer feature — as AI tool configs proliferate across dev machines, having visibility into them is increasingly critical
  7. Read-only matters during incidents — when investigating a malicious package, you don't want your investigation tool to accidentally trigger the exploit
  8. Zero non-standard dependencies — single Go binary, fast installation, no daemon or service to manage
  9. Brand new but promising — macOS and Linux only for now, expect rapid changes, but the core design is sound
  10. Practical workflow — baseline scan weekly, archive NDJSON centrally, deep scan during incidents, search across everything when it matters most
