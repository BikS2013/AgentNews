Stop Using Tailscale. Use Open Source Instead — Deep Dive

Overview

A hands-on walkthrough of replacing Tailscale's proprietary control server with Headscale, the open-source alternative. The video covers the motivation (control, latency, unlimited users/policies), WireGuard mesh networking fundamentals, full Headscale deployment on a K3S homelab cluster, Tailscale client integration, subnet routing for Kubernetes pod access, and DNS strategies for accessing internal services securely.

Why Replace Tailscale? 0:00

Tailscale is amazing — fantastic service built on WireGuard, given away basically free. But its brain is still SaaS. The proprietary control server holds private keys and coordinates the network.

Motivations for self-hosting

  • Control — you control the gateway, not a closed-source server you blindly trust
  • Unlimited resources — users, policies, and other resources are capped on Tailscale's free tier
  • Latency — avoid routing through distant servers when accessing local machines
  • Nerd factor — self-hosting for fun and learning
"I have nothing against Tailscale. For me, it's about latency and control."

VPN vs Mesh Network — Why WireGuard 1:26

Traditional VPN: clients use a gateway to access servers. Incredibly inefficient when you're physically near a machine but the VPN server is far away.

Real-world example: companies running VPNs on AWS US East while having on-prem infrastructure across the country or globe. Same problem at home — why travel across continents to access security cameras?

WireGuard mesh network

Instead of a gateway, forms a mesh of nodes. Every machine that joins runs lightweight WireGuard tunnels between every available pair.

  • Faster — direct peer-to-peer connections
  • Fault tolerant — no single gateway bottleneck

Tailscale builds on this with a coordination server that helps nodes discover each other and stores keys. Headscale replaces only this server component.

Headscale — The Open Source Control Server 1:05

Headscale is one of the most popular projects on GitHub, directly aimed at replacing the Tailscale control center. You keep using Tailscale's open-source client — only the server changes.

Both are based on the same technology (WireGuard). WireGuard alone is hard to set up; Tailscale/Headscale make it easy.

Headscale implements almost all Tailscale features including Magic DNS (automatic internal DNS entries for machines).

Deployment on K3S 2:35

Full deployment walkthrough on a K3S homelab cluster (works on any setup).

Configuration

  • Server URL — publicly available DNS (security handled separately)
  • Listen address for connections
  • Metrics address

Server setup

  • Official Docker Hub container image
  • Command: headscale serve
  • Ports configured to match the config

Caddy reverse proxy

Simple line routing traffic from public domain to local K3S Headscale service.

Magic DNS caveat

While cool for automatic internal DNS, it's problematic in practice. Not all devices trust non-public DNS entries. Browsers especially don't resolve "suspicious" entries. IPs work but are unusable for humans.

Client Setup & First Node 4:14

Steps:

  • Install the standard Tailscale client (open source)
  • Add a UI — Headscale doesn't ship one, but Headplane (most popular option on GitHub) works great
  • Create a user via Headscale CLI: headscale users create <name>
  • Run the CLI inside the container using an alias trick for convenience

First node registration

  • tailscale up with custom login server, accepting routes and DNS entries
  • Visit the generated URL to get a registration command with user and key
  • Register the node on the server
  • Node gets a special internal IP in the new mesh network
  • tailscale status shows the machine as the only node in the mesh

Adding a Subnet Router (K3S Leg) 7:33

Goal: add a node inside the K3S cluster that acts as a subnet router, exposing Kubernetes internal pod networks to the mesh.

Setup

  • Deploy a simple Tailscale container inside K3S called subnet-router
  • Register it with the network using the same domain
  • Add subnets in Headplane to expose Kubernetes internal pod network
  • Approve the subnet routes in the UI

Proof it works

Access Dozzle (open-source log viewer) via its cluster-internal IP from outside the cluster. Tailscale down → access fails. Tailscale up → access restored.

DNS Strategies for Internal Services 9:13

Option 1: AdGuard Home DNS rewrites

Works but browsers don't trust non-standard entries. Fine for ad blocking, problematic for custom DNS. HTTPS adds another layer of annoyances.

Option 2 (Recommended): Public DNS pointing to private IPs

Add a public DNS record (e.g., logs.yourdomain.com) that resolves to a private/internal IP address. If you have Tailscale access, it works. If you don't, the IP leads nowhere. Elegant security: the DNS record is public, but the destination is private.

"DNS is way more trickier than this" — more options for homelab setups will be explored in future videos.

Architecture note

Exposing everything through a single subnet router is a "new VPN problem." Better architecture: deploy a small Tailscale sidecar next to each application you actually want exposed.

Key Takeaways

  • Headscale replaces only Tailscale's proprietary control server — the client stays the same
  • Mesh networks (WireGuard) are fundamentally better than gateway VPNs for latency and fault tolerance
  • Self-hosting gives unlimited users, policies, and full key control
  • Headscale deploys as a simple container with minimal configuration
  • Headplane provides a clean web UI for managing the Headscale network
  • Magic DNS sounds cool but causes real-world browser trust issues
  • Public DNS records pointing to private IPs is an elegant access pattern
  • Subnet routing exposes K8s internal networks to the mesh — but scope it per-app, not cluster-wide
  • The Tailscale client is open source — you only replace the coordination server
  • Self-hosting your network control plane is the natural next step for homelab enthusiasts
